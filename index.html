WastedSpace is a Roblox space sandbox game inspired by Waste of Space. "WoS" in this document always means the original game; everything else is the design for WastedSpace. Where a subsection describes WoS, it says so in its opening line.

1. Universe Generation

The universe is generated on demand. Whenever a region loads, the region and everything in it are derived from one root seed through the seed tree (§1.2).

1.1 Generated on demand

Unmodified terrain, asteroids and space cost 0 bytes in DataStores until a player modifies them.

Nothing is precomputed. The seed tree reaches any node in O(depth) (§1.2), so generating on demand is cheap. A server keeps what it has derived in memory for its own lifetime (as with randmats, §10.4) — that is a cache, not storage, and it is gone when the server shuts down.

1.2 The seed tree

Each seed is derived from the seed above it and the next part of the address: the sector's coordinates, then the region's, then the surface. A terrain chunk adds its position on the surface, and each value of a place, such as gravity, adds its own name. Any node is reached from the root in one step per level, O(depth), with nothing generated along the way: generating the region a player jumped to never requires generating its siblings. That is what makes on-demand generation possible.

A sector holds at most one solar system (§2.1). Whether it has one, its resource richness and where its planets orbit are values of the sector, so its regions exist either way. A planet's surface is derived from its orbit region, so the surface is bound to the orbit that produced it.

Every child of a parent has different inputs, so no two share a seed: coordinates are unique within their parent, the hash covers how many inputs there are, and a value is derived by its name, which can never equal a number or a coordinate.

1.3 Seeds stay on the server

The client never performs hash derivation and never holds seed values, raw or otherwise. The client works only in coordinate space (sectorX, sectorY, regionX, regionY, ...) and sends coordinates to the server for any action (travel requests, etc.). The server is the sole party that ever calls the hash/derivation functions and the sole party that generates terrain/scatter; it streams only rendered results (instances, voxel data) back to the client.

The derivation function is public in practice, so a client holding any hash could regenerate everything below it: with a sector's hash it could regenerate the whole sector, every region, planet, deposit and randmat in it, without ever visiting it. So hashes never leave the server: the client is never a party to any hash value. This is also what lets the server decide what the starmap shows each player.

2. Map & Navigation

2.1 Coordinates

A location is addressed, not positioned: (sectorX, sectorY, regionX, regionY, surface) — universe X/Y, solar X/Y, and which surface, if any. It is written as a comma-separated string, for example 50, -50, 3, -7 or 50, -50, 3, -7, 2.

FieldMeaning
SectorA cell in the universe grid. Each sector holds at most one solar system; its system center is region (0,0) (§3.1).
RegionA cell in the sector's 21×21 subgrid, indexed −10..10 on X and Y. The odd size gives the star a center cell.
surfaceWhich place in a planet orbit region: 0 for the orbit itself, 1 for the planet's surface, 2, 3… for its moons' surfaces (§3.1). Optional: when left out, a Teleporter goes to the planet's surface and a HyperDrive arrives in orbit. Its main user is the Teleporter, which can send players to a teleporter in any of these regions of the same system coordinate, so the number says which one.

WoS's ±100 sector bound came from its packing math. The derivation tree makes the sector space effectively unbounded at negligible cost, so WastedSpace does not inherit it. The 21×21 subgrid stays because that is the design, not a limit.

2.2 Clustering

Systems cluster. Which sectors hold a system, and how rich each one is, is clumped rather than an even scatter: dense clusters of system sectors, with voids of deep space sectors between them. Sparse stretches give hyperjump distance meaning, since a HyperDrive's power cost grows with distance and with the mass of what it carries (§5.5).

Each sector samples a smooth noise field at its own coordinates to get a density, and the sector's seed rolls against that density to decide whether it holds a system. Because the field is smooth, neighboring sectors correlate without depending on each other. A sector with no system is still deep space, with its generated features (§3.6).

Richness follows density. Clusters are both crowded and rich; that is where players trade, compete and fight. Voids are not a destination to flock to — they are where players go to hide and build secret stations, away from everyone else.

Scale is set by jumps, not sectors — for example, crossing a void should take a large share of a mid-game ship's stored power (§5.5).

2.3 Starmap

The starmap shows only the area around the player. Seeing new space means jumping there, so each jump reveals the next stretch — the map is a tool for exploring, not a menu of every destination. The view is to scale with one grid square per sector, and its window is sized together with void size so a player in a void still sees something (§2.2). Solar mode shows the current system.

Cloaking hides a region from the starmap and the telescope only, and not completely: a cloaked region shows only to a player within 3 regions of it. In a void, that makes a cloaked base close to impossible to find. Players can still travel to a cloaked region.

The advanced telescope is late-game tech that detects cloaked regions at sector scale. Within one sector of a cloaked region, it marks that sector on the starmap without showing which region; inside the sector, the 3-region range pins it down. Sweeping a void for one still takes many jumps, each costing power (§5.5).

The map edge glows faintly on the side with more systems beyond it — a direction to head in without revealing what is there. From a distance, a dense cluster is a brighter patch of sky.

3.2 Biomes

Every planet has a biome — its type: Tundra, Desert, Ocean and so on. Biomes are authored, not generated. Each is a designed package: terrain profile, caves, material set, flora, resource table, hazards, skybox, ambient audio.

The hash does two things with them.

Selection. Which biome a planet gets, weighted by orbital position so systems read coherently — hot biomes inward, cold outward. Weighting shifts probability rather than locking the outcome, so outliers occur.

Variation. Within ranges the biome defines. A Tundra planet's seed sets how mountainous it is, how deep the permafrost runs, how much rock is exposed, its gravity, its resource richness. It cannot make the planet stop being Tundra.

Caves come with the biome. The biome sets a range for how much cave its planets have, and each planet's seed picks within it. Most biomes have modest caves; extensive networks appear only where they make sense, such as crystal planets or worlds whose surface is extremely hostile.

A planet's type is fixed at generation and never recomputed.

Tidal locking is a trait, not a biome. Any biome can roll it. A tidally locked planet has no day cycle (§6.3): its sun stays fixed at a time of day set by the planet's seed.

There is no starter biome. WoS had an EarthLike type that existed only to supply spawn planets: limited resources, no randmats, always temperate, natural colors. That is the same mistake as putting RobotDepot in the planet type enum (§4). Starter planets are ordinary Terra planets that pass a filter — temperate, breathable, natural color set, no randmats, not depleted (§13) — and the new-player spawn rotation picks from those. The filter only selects. Starter status never changes how a planet generates, so the rotation can change later without regenerating anything.

Gas giants have no bottom. The surface region is open cloud with nothing to stand on. Gases and fluids can be harvested from the atmosphere into fluid networks (§8), which gives a reason to go there.

The launch list is 18 biomes. WoS shipped nine: Barren, Tundra, Desert, Terra, EarthLike, Exotic, Ocean, Forest and Gas Giant. EarthLike is dropped (above); the rest carry over, and nine are new.

3.4 Planet placement

Two noise fields derived from the sector's seed — a coarse field for broad material clumping, a fine field for local variation — are sampled along the system's orbital radius and combined. A hash-derived threshold cuts the field; local maxima above it become planets, with a minimum separation preventing adjacent peaks merging.

A planet's orbital radius feeds its biome selection weighting, so placement and climate come from the same value.

Measured across 400 systems: planet counts range 1–8, peaking at 4–5. Some systems are crowded, others nearly empty.

3.5 Event regions

discussed, not settled

Event regions hold content that is not generated from the hash tree: PvE encounters, seasonal events, or a beacon signal that leads to a one-off encounter. They live entirely outside the tree. Generation never reads them and they never feed into it, so an event can be added or switched off without changing anything else in the universe.

Beacon signals show up on the starmap and the telescope (§2.3). Following one jumps into an event instance, a separate place outside the universe grid, reached with a normal hyperjump, ship and all (§5). While a beacon is active, any number of players can follow it into the same event, and they can fight each other there. Some events may be PvE only; that is not decided yet.

Players can build freely inside an event instance, but the instance is discarded when the event ends: only what leaves attached to a ship, and what players carry, comes back with them (§5.4). Every instance has an end time, so none becomes a permanent safe haven.

open whether events can also appear inside real regions without changing them.

3.6 Deep space

Deep space holds a variety of generated features. Each Deep Space region rolls from its seed what it holds: nothing, or one of these; whether it holds a wormhole is a separate test, described below the table.

FeatureWhat it is
Rock asteroid fieldRock asteroids to mine.
Ice asteroid fieldIce asteroids to mine.
WormholeA persistent link between two deep space regions far apart, the same for every player and usable both ways.
Pirate outpostArmed NPC structures worth attacking for their loot. Damage to an outpost lasts only while players are there; it repairs fully once everyone leaves. A destroyed outpost stays destroyed for good, and the universe always has more further out.

Wormholes. A wormhole joins two regions far apart, and each end is generated only when its own region loads. Each region decides from its own address whether it holds a wormhole and where its exit is, and the two ends always reach the same answer.

Setup. Space is split into square blocks of 32,768 × 32,768 regions, about 1,560 sectors across. Inside a block, a region's address is its local coordinates (x, y), two 15-bit numbers. The wormhole key is K = hash(root, "wormhole").

1. Every region gets a unique number. A shuffle π turns (x, y) into a number with four rounds of a Feistel network: (L, R) → (R, L ⊕ F(R, r, K)), where F is a hash and r is the round. Each round can be undone whatever F is: from (L′, R′) = (R, L ⊕ F(R)), R = L′ and L = R′ ⊕ F(L′). So π is a bijection and has an inverse, π⁻¹.

2. Every region has exactly one partner. With σ(n) = n ⊕ 1, which flips the last bit, a region's partner is P(a) = π⁻¹(σ(π(a))).

  • P(P(a)) = π⁻¹ σ π π⁻¹ σ π (a) = π⁻¹ σ σ π (a) = a: a region's partner's partner is itself.
  • P(a) = a would need σ(π(a)) = π(a), and σ changes every number, so no region is its own partner.
  • If P(b) = a, then b = P(P(b)) = P(a), so no other region can have the same partner.

3. Both ends reach the same decision. Wormholes are a deep space feature, so only a Deep Space region runs the test. Region a holds a wormhole when all of these are true:

a and P(a) are both Deep Space regions
d_min ≤ dist(a, P(a)) ≤ d_max
hash(K, min(a, P(a)), max(a, P(a))) < T

At b = P(a), the pair is the same two regions, so both are still Deep Space, dist(b, P(b)) = dist(a, P(a)), and the sorted pair is the same. b's test therefore gives the same answer as a's. A region that passes is a Wormhole, and its usual kind roll is skipped; one that fails rolls its kind as normal.

4. The passage goes both ways. If a holds a wormhole, its exit is P(a). Region b = P(a) passes the same test, and its exit is P(b) = P(P(a)) = a.

5. It works at the region level. The test uses only the region's own address, K and fixed numbers, plus the partner sector's value for whether it has a system. No other region is generated, nothing is read or stored, and load order does not matter. The regions' own seeds are not involved, so the seed tree's collision resistance is unchanged. The shuffle scatters partners across the block, so the two ends are unrelated in position and direction.

Checked. Run over every region of a 256 × 256 block, the shuffle gave every region a unique number, every region's partner's partner was itself, no region was its own partner, no pair disagreed about being a wormhole, and all 1,352 wormhole regions (2.06%) came in matched pairs.

Cost. The test is about 11 hashes (4 to shuffle, 4 to unshuffle, 2 for the partner sector's system value, 1 for the pair roll), a distance and a comparison, run once when a Deep Space region loads. A 53-bit MurmurHash3 in native Luau is a few dozen integer operations, roughly 1–3 µs, so the whole test takes about 10–35 µs, under a thousandth of the time it takes to generate the region's terrain. These figures are estimates from the operation count, not measurements.

local K = hash(rootSeed, "wormhole")
local BITS = 15                        -- a block is 2^15 x 2^15 regions

local function F(v, r)
	return hash(K, r, v) % 2^BITS
end

local function shuffle(x, y)           -- (x, y) -> its unique number (L, R)
	local L, R = x, y
	for r = 1, 4 do
		L, R = R, bit32.bxor(L, F(R, r))
	end
	return L, R
end

local function unshuffle(L, R)         -- the inverse of shuffle
	for r = 4, 1, -1 do
		L, R = bit32.bxor(R, F(L, r)), L
	end
	return L, R
end

local function partner(x, y)
	local L, R = shuffle(x, y)
	return unshuffle(L, bit32.bxor(R, 1))
end

-- When a region loads; x, y are its coordinates inside its block,
-- and D_MIN, D_MAX are in regions (300-500 sectors = 6,300-10,500 regions).
local px, py = partner(x, y)
local d = math.sqrt((px - x)^2 + (py - y)^2)
local lo, hi = sortPair(x, y, px, py)
if isDeepSpace(px, py)                -- this region already is: only Deep Space runs this
	and d >= D_MIN and d <= D_MAX and hash(K, lo, hi) < T then
	exit = { px, py }                  -- same block, at (px, py)
end

open block size, distance band and threshold T: the band sets how far wormholes reach compared with a hyperjump (§5.5), and T sets how rare they are.

open more features. Candidates so far: nebulae, radiation zones, crystal fields, derelicts.

Building and terrain share a grid. The 1-stud build grid lines up with the 4-stud terrain cells. Filling terrain is refused in cells under placed parts; digging is always allowed.

Bases stand on foundations. A foundation part attaches to a base's assembly, and clicking it pours a Cement footing: a frustum, widening downward, under the bottom faces of the assembly's parts and into the ground. A base on a foundation stays level when the ground around it is dug away. Digging removes terrain, never parts, so only weapons can break a footing. Cement is barely damaged by explosions, and the lasers that do break it are stopped by EnergyShields.

A base without a foundation rests on the ground. When the ground beneath it is dug out, it falls and takes normal impact damage.

open whether pouring a foundation uses up Cement by volume.

Structures and inhabitants are planned for later, and the manifest is where they go. An NPC structure sits on terrain the same way a player's base does — it does not change how terrain generates. WoS put RobotDepot and RobotFactory in the planet type enum instead, which is why they are permanent placeholders in every universe generated since.

A destroyed pirate outpost is saved only as a destroyed flag in its region's save, never as its wreck: the outpost is generated from the region's seed, so it simply stops being generated (§3.6).

  • open compaction/rebake strategy for heavily-modified regions — an ever-growing delta log has linear replay cost at load time and DataStore has practical size budgets well under its 4MB/key hard limit. Needs a periodic "bake deltas into new base + reset log" strategy before this becomes a real bottleneck, not after.

5. Hyperjump Travel

5.1 One server per region

One server hosts one region for its whole lifetime. Servers aren't assigned regions in advance: a server becomes a region when it starts and is told which one it is. Instancing keeps positions within float32 precision, removes seams between loaded chunks, and gives each region its own part and physics budget, which is what lets large asteroids and ships run. The cost is that everything crossing a jump has to be carried explicitly, and every jump is a loading screen.

A hyperjump leaves the current server. If the destination is already running because someone is there, the player joins that server; otherwise a new one is started for it (§5.3). Either way the player reconnects, and their character and ship are rebuilt on arrival (§5.2).

5.2 Arriving intact

The failures are from WoS. The fixes after them are proposed.

WoS gets the rebuild wrong in several ways:

FailureWhat happens
Apparel and inventory lossWorn accessories detach and are lost. Tools disappear from the hotbar and backpack.
Joints snappingHinges, pistons and ship attachments come apart as staggered part instantiation and velocity spikes stretch constraints past their breaking thresholds.
Rails misbehavingA part on a Rail's moving face — tweened along it like a linear actuator by polysilicon or the microcontroller API — often ends up stuck, welded to whichever ship face it was sitting flush against, along with other wrong behavior.
Players dislodged from seatsPlayers often don't arrive seated where they left (below).

Seating appears to depend on contact: the player loads near the seat and is seated only if they fall onto it. It fails whenever that fall doesn't happen:

CaseWhy the player misses the seat
No gravity generatorNothing pulls the player onto the seat.
Thrust left on, no anchorThe ship flies off before the player lands. Anchors auto-anchor on jump for this reason.
Powered gyroThe ship turns under the player, flinging or dropping them. An anchor stops this too.
Orientation on departureLeaving upside down or nose-up, common when climbing out of a planet, puts the seat beside or above the player, so they fall past it.

Fix: anchored rebuild. Every part spawns anchored, and joints are rebuilt from the saved ship data, never from which faces happen to be touching. Then the whole ship unanchors in one frame, and network ownership is set in that same frame (Roblox doesn't allow setting ownership of anchored parts).

Fix: seat directly. While the ship is still anchored, arrival calls Seat:Sit(humanoid), which welds the player in without any contact, so gravity, thrust, gyros and orientation stop mattering. Every passenger is reseated, not just the pilot: on departure each occupied seat's index is saved with the ship, and on arrival each player goes back into that seat. The ship stays anchored until the passengers who arrived together are seated. A passenger whose teleport had to be retried is seated in their recorded seat whenever they arrive, since Sit needs no contact even on a moving ship.

Worn items and inventory travel in the player's own record (§5.4).

5.3 Starting a region server

Roblox can't start a server and then send players to it. TeleportService:ReserveServer returns an access code, and the server only starts when the first player teleports in with that code.

If nobody is at the destination:

  1. Look the region up in the registry (§A) and don't find it.
  2. Call ReserveServer, which returns an access code and a private server ID.
  3. Claim the region with an atomic compare-and-swap, storing the access code, plus the region's coordinates under the private server ID.
  4. Teleport the players in with the access code.
  5. The new server reads its own game.PrivateServerId, looks up its region, derives the seed and generates.

If the region is already claimed, read its access code and teleport there.

The region isn't sent in teleport data, because the client carries it: Roblox guarantees it came from one of our servers, but a player can reuse it for up to 48 hours, and it belongs to one player's teleport rather than to the jump.

When the last player leaves a server, Roblox shuts it down.

Readiness. A region is claimed before it has finished generating, so arriving players wait on the loading screen until the server reports it is ready. The loading screen shows each step as it happens (deriving the seed, raising terrain, scattering resources), the way Don't Starve does, so a slow region looks busy rather than stuck.

5.4 Carrying the ship

What travels. Everything joined to the hyperdrive's assembly, including anything joined through a CJoint such as a towed ship, plus the contents of its containers, and every seated player. Loose items and standing players are left behind, as in WoS.

Nothing anchored. If the assembly is joined to anything anchored, the jump fails, the same as when the ship itself is anchored. WoS instead carries anchored parts joined by a CJoint, lifting a whole base into orbit with the ship.

Joints travel with their state. Each hinge, piston, rail and CJoint is saved with the ship: which two parts it joins, its settings, and its current position (a hinge's angle, a piston's extension, where a part sits along a rail). The rebuild restores each one at that position, so moving parts arrive exactly where they left. WoS may not do this, which could explain its joint and rail failures (§5.2).

A ship has one owner at a time. Each ship is its own saved record, owned by either a region or a jump in progress, never by a player aboard it; passengers' records only point to it. Only the owner may build it, and handing it over is a single atomic change of owner (§A):

  1. Departure. The origin server saves the ship as in transit on this jump, then removes it from its world before teleporting. From then on the record is the only copy.
  2. Arrival. When the first passenger arrives, the destination claims the record, which succeeds only if it is still in transit on this jump, and builds the ship only after that.
  3. Failed teleport. A passenger whose teleport fails is retried. The origin takes the ship back, with the same claim, only if every passenger failed. A passenger who never gets through stays in the origin region, like a player left standing. Only one claim can succeed, so the ship is built exactly once.
  4. Both servers crash. The record stays in transit. Every passenger's record notes the jump, so whichever of them next joins is sent on to the destination, and the ship is claimed there.

No combination of failures leaves two ships or none.

Parked ships use the same record. A ship left in a region is owned by that region. The region's manifest (§4) lists only which ships are there; the ship record is the truth. On load, a region skips any listed ship whose record names a different owner, so a crash can't leave a ship in two places.

Inventory travels the same way. A player's tools, worn items and inventory are held in their player record and handed over by the same claim, so nothing goes missing on arrival.

5.5 Jump cost

A jump's power cost grows with distance and with the total mass of everything that travels (§5.4), cargo included. The server adds up each part's mass while it walks the assembly, so the cost is cheap to compute, and the HyperDrive shows it before the jump.

The HyperDrive draws the whole cost at once from the ship's power cells. Stored energy therefore sets how far a ship can jump, and a massive ship needs more cells to jump at all. Cells have mass of their own, so capacity has to be weighed against the cost of carrying it.

6. Volumes & Environment

Every part and every player is either inside a sealed volume or out in the ambient environment. Air, heat, corrosion and radiation are all worked out against that one distinction, so a hull does several jobs at once: it holds air, holds or keeps out heat, keeps out a corrosive atmosphere and shields radiation.

6.1 Volumes

A volume is a sealed interior, or the ambient environment outside it.

Sealing is what makes a volume exist. An open-top platform has no interior, so it sits at ambient — the flying board with an air supply bolted to it stops working, with nothing needed to forbid it. Airlocks, hatches and pressure doors become structural rather than decorative, and a hull breach drains air and equalizes temperature in one event.

The same breach lets a corrosive atmosphere in (§6.5), and the interior loses its hull's shielding against ambient radiation (§6.6).

open enclosure test. How the game finds a sealed volume, and what it costs to check again when something is built, broken, opened or closed.

6.2 Boundaries

A volume's boundary is its hull: the layers of parts between inside and outside. Each layer's material contributes three things:

6.3 Ambient

Ambient is what a region supplies outside any volume, set by its biome: a temperature, an atmosphere (breathable, thin, toxic, corrosive or none), a corrosion rate and a radiation level. Space is ambient too, with almost no capacity to carry heat away.

Ambient is not a constant. Its baseline comes from the biome, and it moves through the day/night cycle around that baseline — tidally locked planets have no cycle, so their ambient holds steady at their fixed time of day.

Heat dumped outside raises ambient above its baseline, and ambient drifts back down over time. That gives outside dumping a limit: a large enough operation warms the region it sits in, the gradient shrinks as ambient rises, and radiators shed more slowly the more you run. An industrialized planet is hotter than an untouched one, and cooling gets harder as you scale.

6.4 Air

Air is a property of a volume, the same as temperature. A supply pressurizes the sealed space it occupies rather than projecting a radius through walls, and both systems use the same enclosure test.

Supply size means capacity, not reach — a larger one pressurizes a larger volume, or the same volume faster. On its own, a supply pressurizes only the volume it sits in; other sections get their air through vents.

Vents carry air between sections. A vent is a wall panel on a pipe, and it pressurizes the sealed volume it opens into. An Air Supply sends air down its pipes to every vent on that network, so one supply, or several, can pressurize a whole ship through its bulkheads without equipment in every room. A vent draws air only while its volume is below full, and air never flows back into the pipe; when supply runs short, vents share it fairly (§8.2). A breached room loses its own air, and its vent keeps feeding it until the room is sealed or a valve on that branch is closed, while the rest of the ship keeps its air.

Planets with breathable atmosphere need no supply at all.

An Air Supply needs oxygen piped into it. It uses oxygen to fill a sealed volume and to replace air lost when the volume is opened or breached; a sealed, intact volume stays breathable without more. New ships start with a filled oxygen tank; after that, oxygen comes from electrolysis (§9.6).

6.5 Corrosion

Corrosion is carried by what fills a volume, like air. Toxic atmospheres and seawater corrode the parts they touch, so parts outside a sealed volume or underwater corrode, and parts inside a sealed interior do not. A breach lets the corrosive atmosphere in with the same event that drains the air (§6.1).

Each biome has a corrosion rate, zero on most worlds, and each material a corrosion resistance. Titanium, gold, lead and glass resist it; iron corrodes quickly.

Staged, not ticked. An exposed part has a corrosion age. Past one threshold it is corroded, visibly rusted and weaker; past a second it fails. The server schedules only each part's next stage change, worked out when its exposure starts or changes, and never schedules resistant parts, so corrosion costs nothing per frame. The rust texture blends with age, so a part visibly worsens before its stage changes.

Corrosion continues while a region is unloaded. Stage times are saved, and any that came due are applied when the region loads.

Repair winds the clock back. The repair tool and repair laser reduce a part's corrosion age in proportion to the repair applied, so a partial repair leaves it further from failing and a full repair restores it completely. Repair fixes combat damage first, then corrosion.

6.6 Radiation

Radiation is not carried by air. It passes through walls, reduced by the material in the way, and shielding depends on density and thickness: lead, a thick stone wall or a dense randmat all block it. A boundary's shielding is the sum of its layers, worked out and cached with its insulation (§6.2).

SourceBehavior
Radioactive materialsUranium, plutonium and radioactive randmats irradiate their surroundings, falling off with distance and reduced by any boundaries in between.
ReactorsA source while running. A meltdown irradiates the area around it, fading over time.
Irradiated worldsAmbient radiation throughout the region.

Against ambient radiation, only a sealed volume shields its interior, through its hull's layers. An open structure gives no protection.

Dose. Exposure adds to a player's accumulated dose, which fades slowly. While dose is above a threshold, max health is reduced, more at higher doses. The Geiger counter reads the local radiation level.

Plated apparel. Apparel can carry protective plating, which reduces radiation by its material's density and thickness like any other shielding. A full suit of thick lead plating blocks it completely.

6.7 Personal equipment

A portable supply worn on apparel feeds air to the character directly, independent of any volume. It is a different mechanic from pressurizing a space, not a smaller version of one.

Power comes over antennas, which bridge electricity and trigger signals wirelessly. The same link carries lights, so hands stay free for building tools, and personal heaters and coolers.

This is what makes construction viable on hostile worlds. Without it, building outside needs a hangar larger than the ship, so cost scales with the thing being built. With it you build in the open, limited by power.

7. Heat

Heat is standard gameplay. It gates hostile biomes, limits how fast weapons can fire, forces factories to be engineered rather than assembled, and gives randmat thermal properties something to act on.

7.1 Temperature

Heat belongs to a volume — a sealed interior, or the ambient environment outside it (§6.1).

A volume's temperature is its accumulated energy against its heat capacity. A small sealed room heats quickly, a large one slowly, so factory layout matters without a rule saying so.

7.2 Cooling

Heat is created — a furnace burning fuel, a generator running, a weapon firing. Ordinary parts never delete it: they spread it out or move it elsewhere, in tiers.

PartsWhat they do
CoolersShort range, like a fan. A cooler takes a hot part's heat and spreads it across the parts and air around it, cooling the hot part without moving heat out of the area. While the source keeps running, the area as a whole still heats up.
Heat pumps and heatpipesPump heat out of an area to somewhere else: a radiator, or a heat store (§7.4).
RadiatorsDiscard heat into ambient (§6.3).
Heat storesPlayer-built: copper spreads heat into materials with a high heat capacity, wrapped in strong insulation or a randmat, holding it until it can be dumped.

WoS coolers simply lower temperature while powered, which makes any heat transport pointless. Here spreading heat only buys time, so anything that keeps running needs a way to pump its heat out and dump or store it. Building that chain is the engineering.

Randmats are the exception. A randmat can delete heat outright while powered, a deliberate departure from realism that a rare find earns. How much it deletes rolls like any other property (§10.3).

7.3 Where heat goes

A part is only ever inside a volume or out in ambient. Placement decides its destination, not its type. The same emitter heats a room when it is inside one, warms the planet when it is outside, and radiates into vacuum in space.

Efficiency follows the environment and the gradient. Thick atmosphere carries heat away quickly, thin atmosphere barely does, and vacuum is slowest of all — which is why a ship's ability to shed heat limits how much power it can run.

Since ambient rises as heat is dumped into it (§6.3), a part outside does not warm the planet in any permanent sense; it loses heat to a sink that pushes back as it fills.

7.4 Moving heat

Carried by air. Moving gas moves its temperature with it. Pump warm air out of a factory into a chilled chamber and pump it back — the chiller only has to cool one small volume rather than the whole base.

Carried by heatpipe. Energy moves with no mass — heatpipes carry heat only, and are a separate network from the pipes that transport water, gasoline, steam and other fluids. This is what lets a sealed underground base run combustion generators: heat leaves through a heatpipe to a surface radiator without any opening, so no pressure or breathable air is lost. If heat could only ride on gas, dumping it would mean venting the room.

Heatpipes are configurable as hot or cold transport, so a base runs a hot loop out to radiators and a cold loop back from chillers, and parts connect to whichever they need.

7.5 Materials and insulation

Each material carries two independent numbers.

Resistance is how much it slows heat crossing a boundary. Lateral conductivity is how readily it equalizes with adjacent parts of the same material.

These are separate properties and the interesting builds come from combining them. Copper spreads a hot spot across an entire surface the way copper cookware does. Titanium resists transfer but does not distribute. So a copper inner shell spreads a point source across every wall, a titanium layer outside slows the transfer with no single point under load, and aerogel or cement behind that slows what remains.

A boundary's total resistance is the sum of its layers, which is how real thermal engineering works and is cheap to compute because it is per boundary rather than per part. The same layers also shield radiation and resist corrosion (§6.2).

Lateral equalization is per-part, but narrowly so: one pass over a connected run of the same material, cached until something changes.

7.6 Phase transitions

Matter changes state with temperature:

  • Water becomes ice in a cold enough environment.
  • Water becomes steam in a hot enough one.
  • Ice becomes water when warmed, and steam becomes water when cooled.

Steam is a gas cube that rises, and tanks and bins capture loose items they come into contact with. Players build custom boilers on this: an automatically fueled fire, water sprayed onto it by faucets or ice dropped onto it by dispensers, and a tank above to catch the steam.

A phase change alters an entity's state. It does not destroy one entity and create another. Velocity therefore carries through the transition: ice pushed fast down a copper tube becomes steam still traveling at that speed, and leaves the tube. Buoyancy is a force applied to gas-state matter on top of inherited motion, not a fixed rise speed replacing it.

WoS destroys and recreates, which is why steam stops dead on transition, overlaps with no collision, and trickles into a capture tank one cube at a time. Condensation works the same way in reverse.

7.7 Combat and industry

Weapons heat when fired and stop until they cool, and heat each other by proximity. Packing cheap guns into a compact block becomes self-defeating, because density is what stops them firing. A spread array with cooling beats a brick, and that falls out of the physics rather than a balance rule.

Machinery produces constant heat. An uncooled factory climbs toward lethal, so cooling is part of building one.

open weapon bodies. Proximity heating implies weapons carry their own temperature rather than only heating their volume, a narrow per-part exception like lateral equalization in §7.5.

open uncooled ceiling. Whether an uncooled factory climbs until players die, or plateaus by leaking through its walls. A plateau gives a natural scale limit before cooling becomes mandatory.

7.8 Stars and black holes

A star heats everything in its own region, more steeply the closer it gets, and radiation rises the same way (§6.6), far more around a neutron star. Parts past their material's melting point fail, so flying into a star destroys an ordinary ship. The effect stays within the star's own region: from anywhere else a star is only visible, and the heat it gives the rest of its system is what makes inner planets hot (§3.4).

A rare randmat can change that. A hull whose melting point holds survives inside, and powered cooling or a randmat that deletes heat (§7.2) lets a ship stay for as long as it can keep up. Surviving a star is a capability earned by the find.

A black hole destroys anything that crosses its event horizon.

8. Logistics

Items, fluids, power and heat are the same system with different transport parts. Each is a resource moving through a graph of connected parts, with its own switches, gates, containers and sinks:

Dispensers and faucets release physical items (solids, liquids, or gas you can see and touch until it dissipates) slowly, and only while switched on, by hand, a trigger or a microcontroller. Vents work passively and much faster, and release no items: the gas becomes part of a volume's air (§6.4).

They differ in what flows and which parts connect, not in how the network behaves. One implementation covers all four: a wire network and a chute network are the same solver with a different resource type, and switch, gate and valve parts stop needing per-resource variants.

Heat is included deliberately. It is not a separate system from the rest of §7 — it is a resource network whose resource is heat, and a radiator is its sink the way a dispenser is for solids.

8.1 Why WoS lags

This subsection describes WoS only.

Every tick, every part independently runs a breadth-first search across the whole network for each resource its recipe needs, one search per ingredient, crafts its recipe, then searches the entire network again for somewhere to put the output — continuing until it finds a bin for solids or a tank for liquids. Every bin it takes from or puts into then has its item count updated as well.

Machines also cannot hand items to each other directly. Every output has to go into a bin before the next machine can take it — a pulverizer touching a kiln does nothing until a sand bin is placed between them or shared on the same network.

The number of parts searching and the size of the network each one searches both grow with the factory, so doubling a factory roughly quadruples the work. This is why medium and large builds lag a region to death: it is the wrong complexity class, not a tuning problem.

A dynamic tick rate was added later as a mitigation, throttling from 20/sec to 1/sec on load. It oscillates badly between the two extremes and does not address the cause — each part still walks the entire network, just less often, so throughput collapses while per-search cost stays the same.

8.2 Indexed, event-driven networks

A resource network is a graph problem, not a movement problem. Parts are nodes, connections are edges, and topology only changes when a player builds or breaks something.

Measured against WoS. Both approaches were simulated on the same randomly built factories, from 100 to 10,000 parts on one connected chute network: chutes, bins, extractors and assemblers, two ores and ten part recipes of two to four ingredients in amounts of one to five. Every craft runs every step in both versions: find bins holding each ingredient until the full amount is covered, deduct the amounts, find a bin already holding the output with room or else an empty bin that accepts it, and add the output to it. Extractors do the last two steps for their ore.

The WoS version finds bins by walking the network from the machine, one walk per search. The WastedSpace version reads the network's index, updated whenever a bin changes. Both made exactly the same number of items at every size, so they did the same work.

8.3 At capacity

The one place resources genuinely differ is what happens at capacity, so each resource type declares its own rule:

ResourceAt capacity
Solids, liquids and gasesThe producer sleeps when nothing on its network can take its output — no machine needs it and no bin or tank has room — and wakes when something can.
PowerBrowns out or trips.
HeatSaturates, and coolers stall because they have nowhere to push (§7.2).

8.4 On the dynamic tick rate

Stepping more gradually is better than the 20-to-1 cliff, but oscillation is a feedback problem and finer steps alone will not stop it: the measurement that triggers throttling is the thing throttling changes. If a throttle is kept it needs hysteresis (different thresholds for slowing down and speeding up), asymmetric response (drop fast, recover slowly), and decisions made on a rolling average rather than the instantaneous frame.

Better outcome is not needing one. With event scheduling there is no global tick to throttle — an idle factory already costs nothing. A throttle is worth keeping only as a backstop under genuine overload.

9.5 Power cells and reactors

Power cells come in three tiers, each needing a material from a harder world:

TierBuilt withFound on

3Cobalt, with lithiumScorched planets, where cobalt is abundant

Fission. The Reactor is a fission reactor, as in WoS: uranium, or thorium (§9.1), heats it, and it turns water into steam for SteamTurbines. Lithium target rods placed in a fission reactor slowly breed tritium. Spent rods go into an extractor, which heats them and releases the tritium as a gas into a tank.

Fusion. A fusion reactor is built, not placed. Players build it around a plasma chamber: magnets confine the plasma, a lithium lining with beryllium breeds tritium, and shielding stops its neutrons (§6.6). It burns deuterium, from heavy water (§9.1), with tritium, and produces plasma, which drives a new tier of power generation parts. The build decides how it runs: the magnets set its output and stability, the lining sets its breeding ratio, and the shielding sets how much radiation escapes. Tritium bred in the lining flows out as a gas like any other, to be piped back into the reactor or stored. A lining that breeds less tritium than the reactor burns slowly runs it dry, since fission-bred tritium alone cannot keep up. Stored tritium slowly decays into helium in its tank, so it cannot be stockpiled to make up the difference; the decay continues while the owner is offline. Electromagnets need power and must be kept cold beside the plasma (§7.2); permanent magnets need neither but are weaker. If confinement fails, because a magnet loses power, overheats or is destroyed, the stored energy of the plasma and magnets dumps into the reactor at once as a burst of heat that damages it and nearby parts, and a damaged reactor leaks tritium gas. The gas contaminates the air of the volume it leaks into (§6.1) and harms anyone breathing it without their own air, until the volume is vented; plating does not protect against it. Once that burst is over, nothing keeps heating.

9.6 Electrolysis and hydrogen

An electrolyzer takes water from its pipe network and splits it into hydrogen and oxygen, which go to tanks or straight to machines like any other output (§8). It needs no setting: what it is fed decides what it makes. If either gas has nowhere to go it stops (§8.3), so hydrogen has to be stored, used or vented to keep the oxygen coming. A tier 2 electrolyzer also splits heavy water (§9.1) into deuterium and oxygen, and processes both kinds of water when both are on its network.

Hydrogen rocket. A separate rocket part burns hydrogen from its pipe network. It needs no oxygen and works the same in space and in atmosphere. It is stronger than the Rocket, which keeps burning gasoline.

10. Randmats

A randmat is a material generated for the planet it is found on, with properties rolled from that planet's seed (§10.4). Materials from different planets are different materials, so randmats are something to discover, compare and collect. They give a reason to keep exploring: something other players envy, or a real advantage in base defense or offensive firepower.

10.1 Randmats in WoS

This subsection describes WoS only.

Properties observed in WoS: explodes on contact with a named material (coal, wood, stone); ignites on contact with a named material; emits light on contact with a named material; raises or lowers temperature; radioactive, causing radiation poisoning in proximity. Also unique reflectance, texture, durability and malleability — so a randmat can exceed titanium in strength, or permit larger part sizes than standard materials.

Several never worked. Burn color on ignition did not function. Temperature properties did little, because WoS's heat system was disabled.

10.2 Finding randmats

discussed, not settled

Randmats are common; good ones are rare. Many planets carry a randmat, but most rolls are mediocre and exceptional ones are rare. Exploring keeps paying off, and a great find is worth holding and fighting over (§13). Some planets roll none, which is what the starter filter selects on (§3.2).

Randmats deplete like every resource (§13), so their deposits are rich. A randmat that runs out almost immediately gets used sparingly and then lost, pushing players away from the interesting thing. The answer is not an endless supply but a deep one: a deposit's yield is set by its grade — how concentrated it is — not by how large it looks, and randmat deposits are high-grade, so a host planet provides a substantial amount before it is worked out. That makes an on-site factory worth building and defending: "I found a material" becomes "I hold the planet producing it, for now", which is a better reason for other players to care.

Properties are found by scanning. WoS prints a randmat's properties in its description. WastedSpace hides them until a sample is analyzed by a scanner part the player builds. With randmat properties expanding heavily, finding out what a material does becomes part of the game rather than a tooltip. The scanner is intended to be the same equipment that reads plant genes for gene splicing (§12), so one line of analysis parts serves both.

Randmats are also ingredients. Besides building with them, randmats go into recipes, including crystal growth for lenses (§11), so a rare randmat can give a product nobody else can make.

10.3 Properties

discussed, not settled

Traits hook into systems players already use (heat, power, logistics, combat, air), so a randmat is something to exploit rather than an isolated effect.

Base numbers. Every material has them, and a randmat rolls its own: durability, malleability, volume cap, density, heat resistance, heat spreading, melting point, corrosion resistance, flammability and burn color, plus unique texture and reflectance. WoS already allowed randmats beyond titanium on these.

No ceiling. Each property rolls on a curve with no maximum. Most rolls are ordinary, and the better a value, the rarer it is, but any value can be beaten. The universe has no edge, so there is always a better material somewhere for a player who searches long enough. How fast the odds fall is set per property: the chance of a roll at least x times the typical value is about 1 in xα, so with α = 2 one randmat in a hundred is ten times typical and one in ten thousand is a hundred times. Properties where lower is better, such as density for a light material, roll the same way toward zero, approaching it without reaching it.

Effect curves. Where a raw value would break the game, its effect keeps growing but more slowly the higher it goes, so a better roll is always better and never unlimited: a durability far beyond anything yet found makes a very strong hull, not an invulnerable one.

10.4 Identity and transport

discussed, not settled

A randmat's properties come from its origin region's hash. Moving it to another region, another server, or a bin on the far side of the universe must not change or lose them.

The resolution is that properties are never transported. The address is. Derivation is deterministic and server-side, so any server can recompute a material's properties from its origin coordinates. Properties are not data that has to travel; they are a function of a location every server can evaluate.

AspectHow it works
StorageA stack in a bin or tank is {originRegion, materialIndex, quantity} — a few bytes. No property values are written to the DataStore, keeping randmats consistent with the zero-storage principle (§1.1): nothing is stored that can be re-derived.
StackingTwo stacks merge only if their origin and index match. Materials from different regions are different materials even when their properties are similar, so a bin holds them separately. The identity key is the address, not the property set.
Cross-server transportThe saved ship data carries the same address, never teleport data, which a player can replay (§5.3). The destination server derives the properties itself on arrival. Nothing is synchronized between servers, because both compute the same answer from the same universe seed.
CachingA server derives a material's properties on first use and keeps them for its lifetime. Derivation is a few hashes, and the cache means a factory running thousands of operations per second pays that cost once.
Factory partsParts query properties, never identity. A heat sink asks for thermal conductivity and receives a number; whether it came from a crafted metal table or a hash roll is invisible to it.

open naming. The address is what the machine needs, but a player needs something to call the material. Whether a name is generated from the hash, chosen by the discoverer, or both — and whether a player-chosen name travels with the stack or is local to that player — is undecided.

11. Crystals & Lenses

discussed, not settled

A crafting system of its own, on the same footing as standard materials and parts, built entirely around lenses for energy weapons. It is the crystal counterpart to gene splicing (§12): players grow and design crystals rather than finding a finished product.

Custom energy weapons. Lenses are slotted into a base energy weapon to make it a specific weapon type — beam laser, pulse laser, and everything between. Lenses set damage, shot size, spread and its shape (cone, fan), rapid pulses, bursts, shotgun-style bursts, range, reload rate, area of effect, penetration and thermal behavior. They also set the beam's color: there is no painting a laser — to match a ship, a player grows the lens that produces that color.

Laser crystals heat up and need cooling, which ties the system into weapon heat (§7.7).

Two stages. A source crystal sets color, beam or pulse, pulse rate, damage and heat; shaping lenses set spread, focus, range and beam splitting. Custom weapon types come from combining them.

Production chain, in staged machines that feed each other:

  1. Raw crystal — mined from natural deposits, whose quality and flaws are whatever is found; or grown synthetically from feedstock (mined crystal, minerals, additives) under controlled heat, which is where design control lies.
  2. Cutter — cuts raw crystal to the required spec.
  3. Lens assembler — assembles cut crystal into a finished lens.

Crystal planets are the heart of it: crystal deposits of many types everywhere, alongside the ordinary metals needed to build the machines, so a crystal outpost can supply itself. Quartz and ruby are also among starter resources, so the basics are reachable from the start. Crystal deposits deplete like every resource (§13).

Randmats are dual-purpose — a building material, and an ingredient in recipes, including crystal growth, the way chromium turns sapphire into ruby. A rare randmat can give a crystal nobody else can grow.

Slotting is permanent. A lens is an item that can be traded or sold until it is slotted; once slotted, that is the weapon.

12. Plants & Gene Splicing

discussed, not settled may not survive scoping

Proposed: a seed growing and gene splicing system.

Fits the game because it is the same shape of idea as randmats — find something with rolled properties, work out how to exploit it — but renewable where randmats are extractive and finite. If biospheres vary by biome, what grows where becomes another reason to hold territory.

Intended to feed the same systems as materials rather than running as a separate track: machinery, and thermal management in particular. Specifically raised — lining structures to create a livable ambient temperature on otherwise uninhabitable hot or cold worlds; encasing generators to manage heat creep; wrapping weapons that heat up to extend firing time. Same property, three scales of problem.

open whether the thermal material is a randmat, a grown plant, or both — this decides whether hostile-world access is extractive and territorial or renewable and portable.

13. Gameplay Loop

Progression is only what you have. There are no levels, research trees or unlocks. A player is further along because of their materials, their builds, what they know how to engineer, and the planets they hold. A new player who gets the materials can build anything.

The loop:

  1. Start on a Terra starter planet with basic resources (§3.2).
  2. Mine, refine and build a first ship from what is nearby.
  3. Go further out. Harder worlds are gated by engineering, not levels — an unbreathable or hostile world can only be worked once you can build the air, sealing and cooling it needs (§6, §7).
  4. Find what is valuable. Randmats and rare resources sit on remote or hostile worlds (§10.2).
  5. Hold what produces it. An on-site factory turns a find into a planet you hold, which gives other players a reason to trade with you or come after you (§10.2).

Resources deplete. Deposits are finite: once mined out, they are gone for good. There are no static deposits that last forever. This drives exploration and migration to new planets, and makes building and defending outposts and supply operations a skill worth practicing. Depletion is a player modification, so it is saved through the region's delta log (§4); an untouched deposit still costs nothing to store.

Trade is barter. There is no currency. Players exchange materials, parts and ships directly, at whatever they agree on. Exchange is physical — dropping items, loading bins, handing over ships — with no trade window. Trust is part of the game, and so is being scammed.

Holding a planet is physical. There is no claim or ownership system. A planet is held by having a base, defences and people on it, and anyone who can beat what was built there can take it.

Bases are always vulnerable, including while their builders are offline. Bases persist with the region (§4), so automated defences — turrets, microcontroller-driven systems — are the only protection while nobody is home.

open starter harassment. In WoS, starters are attacked not for loot (starter planets hold only basic iron, copper and stone-based resources) but as bait: factions formed to protect new players, so veterans looking for a fight attack starters to draw those factions in. Hiding starters does not work — anyone can start a new game and read the rotating roster and its coordinates. Two remedies are on the table: make faction holdings in rich clusters easy to find and worth attacking, so they are a better way to start a fight than bait; and protection that follows the new player rather than the place — they and what they build cannot be damaged by other players until their first hyperjump or a time limit, ending at once if they attack anyone.

Implementation Notes

Everything below is for developers working on the codebase. Nothing here is design.

A. Registry, Ship Records & Atomic Claiming

  • Registry maps RegionHash → access code, and PrivateServerId → region coordinates so a new server can find out which region it is (§5.3).
  • Must use MemoryStoreSortedMap:UpdateAsync — atomic compare-and-swap, not a GetAsync read followed by a SetAsync write. Two servers can both read "unclaimed" before either write lands, and SetAsync overwrites without checking, leaving two servers each believing they host the region and independently diverging.
  • TTL/expiry or heartbeat refresh needed so a crashed server doesn't leave a stale claim that misroutes future players indefinitely.

The consequence of getting this wrong is worse than a duplicate server. Both claimants would generate the same region independently and diverge — the same asteroid mined twice, two versions of the same place, with the registry pointing at only one of them.

Ship records (§5.4) live in a DataStore under Ship_{Id}, with the owner field (region or transit, jumpId) in the same value as the ship, so one UpdateAsync both checks and changes ownership. Ships are packed with buffer like region deltas (§4); a value holds up to 4 MB, far more than any ship needs. Player records use the same claim for inventory.

MemoryStore is not used for ships even though it is faster. Items are capped at 32 KB, data expires, and writes fail once the experience's quota (64 KB + 1.2 KB per player) is full, any of which would lose a ship mid-jump.

C. Seed Derivation

The design is in §1.2.

Seed_child = Hash(Seed_parent ‖ Inputs)
  • Hash width: 53 bits, so each hash fits exactly in one Luau number and can seed a generator directly. Internally the hash function works in 32-bit pieces with Luau's bit32 library and combines them into the 53-bit result. Places that share a hash generate identically, so the width decides how often duplicates appear: at 32 bits two places are as likely as not to share a hash after about 77,000 places, at 53 bits only after about 100 million.
  • Hash function: MurmurHash3's 128-bit variant for 32-bit platforms, which works entirely in 32-bit operations; 53 bits of its output form the hash. Inputs here are short, fixed-size coordinate tuples where adjacent values differ by a single bit, which is the case Murmur3 was designed for. It mixes such inputs thoroughly, processing four bytes per round, so each call stays cheap.
